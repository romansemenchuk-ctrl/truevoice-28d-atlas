# TrueVoice Academy — Neon Membership Design

Дата: 08.09.2026. Версія: 1.1.
Статус: інфраструктуру створено; специфікація серверної реалізації — для перегляду.
Цей документ замінює Supabase-специфічні рішення версії 1.0, а не оголошує кабінет готовим.

## 1. Фактичний результат

Через підключений Neon перевірено всі повернуті організації. Доступна організація `Roman`, план `free`; інших організацій це підключення не повернуло. До створення список її проєктів був порожній.

Створено `truevoice-academy`, AWS Frankfurt (`aws-eu-central-1`), PostgreSQL 17. Початкова та єдина гілка — `staging`; база — `truevoice`. Межі обчислення: 0,25–0,5 CU. План організації не змінювався. Платні доповнення не підключалися.

Незалежна перевірка після створення підтвердила гілку `ready`, базу `truevoice` та виконання SQL: PostgreSQL `17.11 (32e7196)`, прикладних таблиць — 0. Облікові дані підключення не запитувались і не додаються до цього документа. Поточна власницька роль призначена для адміністрування, не для майбутнього браузерного доступу.

Перший запит відхилено через явне налаштування інтервалу засинання, заборонене на цьому Free-акаунті. Після повторної перевірки відсутності проєкту створення виконано без цього параметра. Політика засинання залишена провайдеру; новий тариф не знадобився. Проєкт-дубль не створювався.

Не виконано: прикладні міграції, інтеграція Better Auth, SMTP, імпорт покупців, запис секретів Vercel, переключення WayForPay, новий UI або production-деплой. Успішний SQL-запит перевіряє базу, не авторизацію.

Вихідна версія застосунку: PR №1, `upgrade/anatomy-interactive-20260908`, commit `ea4bb05fb5e54157339205c10f6bc5744ea8fcde`. PR відкритий, не злитий. Репозиторій атласу публічний. Код версії 3.0 у цьому етапі не змінено; старі тести не вважаються тестами нового кабінету.

## 2. Рішення та межі

Контур: браузер → Vercel Node.js backend → Better Auth + Neon PostgreSQL. Зберігаємо наявний фронтенд та 28 уроків. Переписування на інший UI-фреймворк не потрібне для заміни бази.

Обраний напрям — власний екземпляр бібліотеки Better Auth із PostgreSQL та Email OTP. Керований Neon Auth — інший варіант; його не було увімкнено і не слід паралельно додавати як друге джерело особи. Документація Better Auth підтверджує PostgreSQL-адаптер і вхід поштовим кодом [S2, S3].

Браузер не отримує SQL credentials, privileged ключі або доступ до Neon Data API. База не є сховищем аудіо: у першому релізі голосові записи залишаються на пристрої. Прогрес, нотатки й закладки синхронізуються через сервер.

Платні опції, масові листи, реальні клієнтські дані в staging та зміни live checkout заборонені без окремого погодження. Free — обмежений ресурс, не гарантія необмеженого безплатного production. Офіційний тариф на дату перевірки: $0, 0,5 GB та 100 CU-год/місяць на проєкт; запуск не вимагає переходу на платний план [S1].

## 3. Особа, вхід і сесія

Користувач вводить пошту покупки. Видачу сесії кабінету дозволяємо після підтвердження пошти й перевірки чинного права доступу або серверної ролі адміністратора. Наявність контакту в SendPulse не є підтвердженням оплати.

Планована конфігурація входу: код із 6 цифр, 5 хвилин дії, максимум 3 невдалі спроби для одного коду; повторна видача обмежена за адресою та джерелом запиту у стійкому сховищі. Одноразовість і генерація належать Better Auth, не самописному генератору. Зберігання OTP — hashed; налаштування бібліотеки перевірити тестом, не покладатися на значення за замовчуванням [S2].

Відповідь на запит коду однакова для відомих і невідомих адрес. Поштову доставку виконувати через надійний outbox/чергу з обмеженим строком життя, не через незавершений Promise після повернення serverless-відповіді. Коди, токени й адреси покупців не потрапляють у публічні логи.

SMTP/транзакційний поштовий канал не налаштований. До вибору нового сервісу перевірити наявний SendPulse-канал саме для транзакційних листів; адресна книга та бот не доводять доступність SMTP. Без перевіреної доставки на контрольну зовнішню адресу запуск для студентів закритий. Тести використовують локальний поштовий адаптер, не листи покупцям.

Сесією керує Better Auth; не створювати другу самописну систему cookie поверх неї. Для серверного доступу потрібні захищені cookie, точний список дозволених origin, CSRF-захист змін стану, актуальна перевірка сесії та entitlement на кожному приватному маршруті. Строк сесії першого релізу — 12 годин без автоматичного подовження; це проєктне рішення, яке має бути відтворене у конфігурації й тестах.

Роль, покупки та права не є редагованими полями профілю. Відкриті auth-endpoint не повинні обходити перевірку покупця. Адміністратора прив'язувати до явно підтвердженого ID користувача; «перший зареєстрований — адмін» заборонено. Адмін теж починає зі студентського вигляду; внутрішній розділ доступний лише після серверної перевірки.

Після logout, зміни акаунта або втрати доступу припинити практику, мікрофон і приватні запити. Пізня відповідь попереднього акаунта не повинна з'являтися в новому. Відкликання доступу не видаляє авторські нотатки; їх отримання організувати через контрольований запит підтримці, не публічний endpoint.

## 4. Дані й SQL-ізоляція

Схему Better Auth генерувати із зафіксованої версії бібліотеки, вибраних плагінів та актуального адаптера. Не переносити `auth.users`, Supabase RPC або ролі `anon/authenticated/service_role` як нібито наявні в Neon. Neon — PostgreSQL, а не сумісний endpoint Supabase Auth.

Прикладна модель: `profiles`, `member_roles`, `products`, `product_grants`, `orders`, `payment_events`, `entitlements`, `lesson_progress`, `lesson_notes`, `bookmarks`, `audit_log`, `outbox`. Особисті записи прив'язані до незмінного user ID; email потрібен для підтвердження первинного зв'язку покупки, не як універсальний зовнішній ключ.

Права прив'язані до конкретного ресурсу й замовлення. Профілі, сесії та записи авторизації не дають права на весь контент. Інші придбані продукти не розблоковуються автоматично.

Окремі SQL-ролі для міграцій, auth-сервісу, користувацьких операцій і платіжних операцій. Runtime не використовує власницьку роль `truevoice_owner`. Немає browser SQL access. Приватні таблиці користувача мають RLS і явні мінімальні grants; runtime-роль не володіє таблицями і не має BYPASSRLS [S4].

Контекст користувача задає лише сервер після перевірки сесії, в межах тієї самої транзакції та того самого з'єднання. Контекст має скидатися після транзакції, особливо в connection pool. Клієнтський `user_id` не приймається як доказ. Цей механізм захищає від помилкового міжкористувацького доступу, але не замінює захист від SQL injection чи викрадення серверного credential.

Тести RLS виконувати під реально обмеженою runtime-роллю для користувачів A/B та без контексту. Перевірка під власником бази не підтверджує ізоляцію. Платіжна роль не читає нотаток; auth-роль не видає entitlements. Зміни ролей і прав журналюються.

## 5. Покупки та попередні клієнти

Наявний WayForPay backend лендингу зберігається. Пошту, товар, ціну, валюту та reference фіксує довірений сервер до відправлення на оплату. Подія провайдера має бути перевірена за актуальним протоколом, звірена з цим замовленням та надійно записана до підтвердження прийому. Email із непідписаного поля callback не підміняє збереженого покупця.

Унікальні ідентифікатори подій і транзакційна зміна entitlement забезпечують повторюваність. Повторне повідомлення не створює другої покупки. Втрата доступу до бази не перетворює подію на «успішно доставлену». Після надійного запису outbox дозволяє завершити доставку доступу й наявний SendPulse-сценарій повторно.

Повне повернення або chargeback відкликає права лише відповідного замовлення. Інша активна покупка може зберігати доступ. Старий Approved не відновлює відкликане право. Часткові повернення, невідомі статуси й суперечливі події потрапляють на звірку, а не в довільне автоматичне рішення.

Каталог передбачає доступ до базового атласу від погоджених продуктів Mini. Доплата `mini-upgrade` не прирівнюється до повної покупки без підтвердженої бази. Строк дії визначається умовами конкретного продукту; «7 місяців» не переноситься на всі ресурси. Точна матриця строків і грантів — обов'язковий пункт перед live-запуском; до її затвердження реальні права не видаються.

Для старих клієнтів потрібний довірений експорт замовлень із reference, продуктом, email, сумою, валютою та датами. Dry run показує дублікати, невідомі продукти й суперечності; потім автор погоджує конкретний імпорт. Контакти розсилки без платіжної підстави не активуються. Імпорт та звірка не відправляють масових листів.

## 6. Приватний контент і кабінет

Закриті уроки та внутрішні методологічні поля не копіюються в `dist`, відкриті JS-файли або source maps. Студентська відповідь формується явним списком дозволених полів; admin-дані — окремим захищеним маршрутом. Приватні відповіді не потрапляють у спільний CDN-кеш. Ілюстрації, оголошені частиною платного контенту, також видаються після перевірки права, а не прямим публічним URL.

Поточний репозиторій атласу публічний, і новий логін не відкличе копії вже опублікованих матеріалів. До розміщення нових закритих матеріалів потрібне окреме рішення про приватний репозиторій/приватне джерело й старі відкриті деплої. Не змінювати видимість, історію або чужі проєкти автоматично.

Кабінет: продовжити урок, мої продукти, прогрес, закладки, нотатки, локальні записи голосу, профіль і підтримка. Не показувати вигаданий прогрес чи фіктивні покупки. Синхронізація — за ревізією запису уроку; конфлікт двох пристроїв не стирає текст. Інтерфейс розрізняє локальне збереження, синхронізацію та помилку.

Старі browser-local записи не приписуються першому акаунту автоматично: потрібний явний імпорт власником. Аудіо залишається локальним і має окреме завантаження; JSON резервної копії його не містить. Другий акаунт на тому самому пристрої не бачить записів першого.

## 7. Дизайн, анатомія й практика

Зберегти напрям наданих moodboard, `7d.truevoice.academy` та `thinkside-rumezhak-proposal`: чорна основа, червона органіка, типографічний контраст, тонкі лінії, контрольована глибина. Оригінальна монограма Сонце/Місяць/вісь береться з лендингу, а не генерується заново. Візитка серед наявних вкладень не знайдена; її врахування не позначається виконаним і не блокує backend.

Вхід і головна кабінету можуть мати делікатні частинки й орбіти. Уроки, форми й підписи — на спокійному тлі. Практика — лише інструкція, ритм, час і зупинка. Немає обов'язкового boot-екрана, звуку наведення, сильного нахилу робочих карток чи спалахів. Зменшення руху та прихована вкладка зупиняють декоративні ефекти; сенсорне прокручування не перехоплюється.

Художній шар не є клінічною анатомією. Для структури синхронізувати кнопку, точку, підпис, схему й пояснення; координати перевірити на кожній карті. Анімація діафрагми, фаза та дихальний лічильник використовують один стан часу. Умовна уповільнена фонація — окрема демонстрація, не «голосові складки в темпі вдиху».

Пауза зберігає позицію; reset повертає початок; нульові фази пропускаються. Навігація, logout, зміна акаунта й закриття режиму прибирають старі таймери/слухачі/мікрофон. Повторне завершення вправи не знімає відмітку. Зміна HUD не перезапускає практику. Zoom/pan, клавіатура, touch та Escape залишають керування доступним.

## 8. Приймання й межі запуску

Це заплановані перевірки, не результати виконаних тестів:

- OTP: невірний, повторний і прострочений код; ліміти; прямий обхід auth-route; CSRF і сторонні redirects.
- Доступ: гість, покупець, прострочення, refund, адміністратор, підміна ролі/ID через браузер.
- SQL: користувач A не читає/не змінює даних B; без контексту — deny; контекст не переходить у наступний pooled-запит.
- Платежі: дубль, неправильна сума/валюта/email, reorder, тимчасова помилка БД, відновлення outbox, друга чинна покупка.
- Збірка: немає приватних уроків/секретів у статичній видачі; усі 28 оригінальних уроків збережені на сервері.
- Кабінет: reload, зміна пристрою, конфлікт нотаток, logout під час запиту, явний імпорт старого прогресу.
- Інструменти: всі карти й точки, zoom/pan, pause/reset/navigation, background tab, завершення таймера, відмова/скасування мікрофона.
- Доступність: 320/390/768/1440 px, видимий focus, Tab/Escape, reduced motion; Chromium/WebKit плюс окремий фізичний iPhone.
- Пошта: контрольна зовнішня адреса отримує код; доставка не залежить від відкритої вкладки.

У staging — лише синтетичні покупці. Реальний SMTP, матриця прав і строків, джерело історичних замовлень, підтверджений admin ID та приватне джерело контенту є контрольними пунктами перед live. Їхня відсутність не блокує локальні тести, але забороняє оголошувати готовий production-кабінет.

## 9. Наступний етап

Проєкт уже створено: повторне створення не потрібне. Після перегляду цієї специфікації — деталізований implementation plan, потім версіоновані міграції й тести в `staging`, реалізація поштового входу та приватної видачі контенту. Власницькі credentials не використовувати як runtime-секрет. Секрети зберігати лише у відповідному серверному середовищі; не надсилати їх у чат.

Далі кабінет і синхронізація, потім ілюстрації/механіка/ефекти. Перемикання робочого домену та платіжного callback — окремий погоджений етап після тестування. Цей документ не змінює production і не стверджує, що наступні етапи вже виконані.
